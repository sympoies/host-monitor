## 2026-10-02 - 0.6.0: Android devices over a collector host, offline alert for broken collection

### Result
- `package.json` version 0.6.0. An `adb` host entry may also carry an `ssh` alias and an absolute `adb.bin`. The server then runs the same read-only script through one `ssh <alias> <bin> -s <serial> shell '<script>'` call, so a phone attached to another collector host is monitored without anything running on that host. The alias and serial stay allowlisted, and a remote entry without an absolute `bin` never reaches the runner.
- A host entry may set `offlineAfterSeconds`. For an `adb` device it enables the offline alert after that long without a successful collection, with the usual recovery message. Without it an adb device still never alerts offline.

### Why / context
- The Android test device moved from the server's USB to a collector host's USB. The server's local `adb -s <serial>` then failed with `collector-unavailable` and the dashboard said `offline`, as it does for an unplugged phone. Because the device is not always on, no alert fired, so a configuration break sat unnoticed.
- A detached phone and a broken collection path fail the same way from the server (adb reports the device as not found), so the two cannot be told apart by the error. They differ in duration: a phone is normally back within hours, a configuration break never recovers. A per-device threshold of a few hours is the smallest rule that separates them. The error text stays out of alerts, history, and `/api/fleet`.
- Consumers: no entrypoint or Node change, and no collector change. Only the server configuration gains the optional keys; a collector host does not need 0.6.0.

### Evidence
- Test first: the remote-adb command, the remote-entry allowlist, and the per-device offline alert tests in `test/server.test.ts` failed before the change. `npm run validate` passes with 91 tests.

## 2026-10-01 - 0.5.0: grace window and restart loops

### Result
- `package.json` version 0.5.0. A new attention item is recorded and alerted only after it has lasted its grace window: `alerts.graceSeconds`, default 90, with per-item `alerts.graceOverrides` matched by host, kind, and title. An item that clears inside the window leaves no event and sends no recovery.
- Restart loops still alert. The collector now reports each systemd service's `NRestarts` as the optional snapshot field `restarts`. When a service restarts `alerts.restartLoop.restarts` times (default 3) within `windowSeconds` (default 600), the server alerts it as `restart loop · 3 restarts in 10 min`. Items without a counter, such as probes, alert as `flapping` after the same number of new failures. The incident recovers once a full window passes without a restart, so a steady loop is one incident.
- Items found on a host's first observation are a silent baseline: they now also recover silently, so a recovery is only ever sent for an item that alerted.

### Why / context
- On 2026-10-01 two self-healing restarts paged the Monitoring group. At 10:02 on a collector host, `agent-console-collector-a-serve.service` exited 75 after its binary was replaced, and systemd restarted it 5 s later. The service alert and the "Agent Console session execution" probe alert both fired, then recovered. At 11:34 on the server, `agent-console-speech.service` was restarted, its model took about 10 s to load, and the "Agent Console speech" probe alerted and recovered about a minute later.
- Why 90 s: the self-healing restarts above are over within a minute. The window is measured in time, so it means the same at every refresh interval (the server 60 s, a collector host 300 s). A real outage alerts on the first collection at least 90 s after it was first seen: about 2 minutes on the server, and the second collection on a collector host.
- Why count `NRestarts`: a collector host is collected every 5 minutes, so collections cannot see a 5 s restart, let alone three of them. The counter records every automatic restart between collections. A service with a counter counts restarts only from it, so one crash that is seen both as a failed unit and as a counter step counts once.
- Review found three defects before merge, each now covered by a test. A steady loop recovered and alerted again on every restart. A cleared baseline item was never saved, so after a server restart its return stayed silent. Restarts counted while a host was unreachable were all stamped at reconnect.
- Consumers: no entrypoint or Node change. The new keys are optional, and the server accepts snapshots from older collectors, falling back to failure counting without `restarts`. A collector host needs 0.5.0 to report restart counters.

### Evidence
- Test first: the new tracker, configuration, and end-to-end tests in `test/alerts.test.ts`, and the `NRestarts` collection test in `test/model.test.ts`, failed before the change. The end-to-end test replays a collector host restart: a unit seen in `activating · exit-code` with one counter step sends nothing.
- `npm run validate` passes with 88 tests.
